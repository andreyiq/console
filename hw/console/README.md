# hw/console — схема платы v2 в KiCad 9

Открывать: `kicad hw/console/console.kicad_pro`.

## Источники истины

Ровно три, больше ничего:

| | |
|---|---|
| **Даташит** | `docs/mangopi/f133_datasheet_v1.2.pdf` и `docs/chips/<партномер>_<LCSC>.pdf` |
| **MangoPi** | `docs/mangopi/mq_sch_v1.6.pdf` — серийная плата на том же F133-A |
| **Xassette** | `../ref/Xassette-Asterisk/` — вторая живая плата на F133 |

Всё остальное — не источник. В частности [`../BOARD-draft.md`](../BOARD-draft.md)
**недостоверен**: он писался по ходу дела, мешает проверенные числа с
рассуждениями, и в нём уже находилось прямое противоречие самому себе.
Ссылаться на него нельзя, он оставлен как список тем для перепроверки.
[`../TZ.md`](../TZ.md) отвечает только на вопрос «что должно быть на плате»,
[`../CHIPS.md`](../CHIPS.md) — «какие микросхемы», ни один из них не источник
электрических решений.

**Правило: ни одного номинала и ни одной цепи без ссылки на источник.** Если
факта нет ни в даташите, ни на двух платах — это не факт, а допущение, и оно
помечается как допущение вместе с тем, чем рискуем.

## Порядок работы — по блокам

Блок = микросхема (или группа) из [`../CHIPS.md`](../CHIPS.md). На каждый блок
заводится документ в [`blocks/`](blocks/) с жёсткой структурой:

1. **Микросхемы** — какие пункты CHIPS.md закрывает блок
2. **Из даташита** — выдержки с номером таблицы или параграфа
3. **MangoPi** — что реально сделано, с номером страницы и позициями
4. **Xassette** — то же, с refdes из нетлиста
5. **Расхождения** — где референсы спорят друг с другом или с даташитом
6. **Что рисуем** — решение, каждая строка со ссылкой на пункты выше
7. **Допущения и открытые вопросы** — всё, что не подтверждено источником

Итерация: собрать документ блока → обсудить открытые вопросы → дополнить
[`../CHIPS.md`](../CHIPS.md) закупкой → нарисовать блок → показать глазами →
ERC и netlist → следующий блок.

| Блок | Микросхемы (CHIPS.md) | Документ | Статус |
|---|---|---|---|
| 1 Кнопки | — | | |
| 2 Питание | §2 `SY8089AAAC`×3, §3 `TP4056`, §7 движок, §8 банка, §10 power path | [02-power.md](blocks/02-power.md) | **нарисовано**, 48 деталей |
| 3 USB и FEL | §9 `USBLC6-2SC6` | | |
| 4 Хранение | §6 `W25Q32` | | |
| 5 Звук | §5 `PAM8301` | | |
| 6 Дисплей | §4 подсветка | | |
| 7 Такт и сброс | — | [07-clock-reset.md](blocks/07-clock-reset.md) | **нарисовано**, 10 позиций (одна не монтируется) |
| 8 Развязка и КТ | §1 `F133-A` | | |
| 9 UART, JTAG, светодиоды | — | | |

## Как устроен лист

**Один лист A2**, `console.kicad_sch`. F133 целиком в середине, обвязка вокруг
него девятью блоками в пунктирных рамках. Раскладка скопирована со стр. 3 схемы
MangoPi (`docs/mangopi/mq_sch_v1.6.pdf`) — это плата на том же чипе, и она
устроена так же.

Правило раскладки: **блок стоит с той стороны корпуса, откуда выходят его
выводы.** Символ повторяет корпус, поэтому сторона известна заранее:

| Выводы | Сторона | Блок |
|---|---|---|
| 1..6, 118..128 `PG` | лево-верх и верх-лево | 1 Кнопки |
| 7..13 `PF`, 14..19 `PC` | лево | 4 Хранение |
| 20..30 PLL/DCXO/RTC/LDO | лево-низ | 7 Такт и сброс |
| 31..45 `PE` | лево-низ и низ-лево | 9 UART, JTAG, светодиоды |
| 46..51 SYS/DRAM | низ-центр | 8 Развязка и контрольные точки |
| 52..76 `PD` | низ-право и право-низ | 6 Дисплей |
| 87..100 аудио | право-верх | 5 Звук |
| 101..117 ADC/USB/CORE | верх | 2 Питание, 3 USB и FEL |

Раскладка задаёт только геометрию. Что внутри блока — в его документе
в [`blocks/`](blocks/).

## Как соединяется

Проводов между блоками нет — всё на **глобальных метках**, как у MangoPi. Для
128-выводного чипа это единственный читаемый вариант: цепь называется один раз
у вывода F133 и один раз у потребителя, а не тянется через весь лист.
Локальные провода — только внутри блока (делитель, RC, развязка).

## Библиотеки

Обе локальные, лежат в `lib/`, подключены через `${KIPRJMOD}` — проект
открывается на любой машине без установки библиотек.

| | |
|---|---|
| `lib/console.kicad_sym` | символ F133-A. Генерируется, руками не править |
| `lib/parts.kicad_sym` | то, чего нет в штатных библиотеках: `SY8089AAAC` (по даташиту) и рельсы `VSYS`, `+0V9`. Пишется руками |
| `lib/console.pretty` | футпринты платы. `eLQFP-128 ... EPAD_5.72mm` взят из `../lib/allwinner_SiPs_kicad_lib` и обновлён до формата KiCad 9 |

### Символ F133-A

Собирается скриптом из распиновки даташита:

```
python3 hw/console/tools/gen_f133_sym.py
```

129 выводов (128 + `EPAD`), один юнит, корпус 119 × 114 мм. Выводы разложены
**в порядке нумерации eLQFP128** — 1..32 слева сверху вниз, 33..64 снизу слева
направо, 65..96 справа снизу вверх, 97..128 сверху справа налево. Проверено по
футпринту: лапка 33 в левом нижнем углу, 97 в правом верхнем. То есть символ
читается как сам корпус, и при разводке сразу видно, с какой стороны выходит
цепь. Функциональные зоны нарисованы поверх — короткой линией от края и
подписью.

Исходник распиновки — `F133_Datasheet_V1.2.pdf`, таблица 4-2. Библиотека
Xassette (`../ref/Xassette-Asterisk/hw/lib/F133.lib`) использовалась для
сверки, в ней нашлись три расхождения с даташитом, здесь они исправлены:

| Вывод | У Xassette | В даташите |
|---|---|---|
| 47 | `DZQ` | `NC` — калибровочного резистора DDR не нужно, память внутри корпуса |
| 51 | `VDD-SYS0` (дубль) | `VDD-SYS1` |
| 25 | `XX32KIN` | `X32KIN` |

Плюс к этому в символе:

- **выводы 108–111 помечены `no_connect`** — CVBS IN есть только у F133-B,
  у нашего F133-A это NC (даташит, сноска к таблице 4-2). Вывод 107
  `VCC-TVIN` под сноску не попадает: это питание блока, таблица 5-2 задаёт
  для него 1.8 В, и обе референсные платы его подключают — тип `power_in`;
- **`EPAD` = `GND`** — отдельных выводов земли у корпуса нет, вся цифровая
  земля идёт через термопад. Значит термопад обязан быть пришит переходными
  к нижнему слою, это не только теплоотвод;
- **вывод 27 `RESET`** — тип `I, OD`, домен **`VCC-RTC` = 1.8 В**, не 3.3.
  Подтяжка и кнопка сброса должны сидеть на `+1V8`.

## Каркас листа

```
python3 hw/console/tools/scaffold.py
```

Одноразовый скрипт: создаёт лист, рамки блоков, таблицы библиотек и ставит
F133. Уже существующие файлы **не трогает** — схему, которую правили руками,
он не затрёт. UUID детерминированные, поэтому на чистой папке результат
повторяется побайтово.

`console.kicad_pro` скриптом не создаётся — он взят от платы v1 и почищен.

Две грабли, на которые скрипты уже наступили и больше не наступают:

- **координаты символа обязаны быть кратны 1.27 мм.** Середина A2 — это 297.0,
  что не кратно, и все 129 выводов уезжают с сетки (`endpoint_off_grid`).
  Берём 297.18 = 117 × 2.54.
- **`(justify center)` в свойстве символа парсер библиотеки не принимает** —
  библиотека молча перестаёт грузиться целиком. По центру и так по умолчанию,
  просто не указывать.

## Сверка с референсом Xassette

`kicad-cli` схему Xassette не открывает — это legacy-формат KiCad 5. Поэтому
свой разбор:

```
python3 hw/console/tools/xassette_net.py U1 U3 U4 U5   # цепь на каждом выводе
python3 hw/console/tools/xassette_net.py --net +1V8 +3V3   # состав цепи
```

Цепи собираются union-find'ом по концам проводов, junction'ам, меткам и
power-символам. Схема MangoPi доступна только как PDF, её читаем через
`pdftotext -bbox` (координаты меток) и `pdftoppm` (кроп нужного узла).

Что уже вытащено этими двумя способами — в документах блоков, [`blocks/`](blocks/).

## Проверка

```
kicad-cli sch erc           -o /tmp/erc.rpt      hw/console/console.kicad_sch
kicad-cli sch export netlist -o /tmp/console.net  hw/console/console.kicad_sch
kicad-cli sch export pdf     -o /tmp/console.pdf  hw/console/console.kicad_sch
```

Сейчас нарисованы блоки 2 и 7: ERC даёт 160 нарушений, и все они, кроме одного, —
на невыведенных пока выводах F133; число должно падать по мере работы.
Единственное исключение — `VBUS` без источника: он появится в блоке 3 вместе
с разъёмом USB-C.

**Netlist смотреть обязательно, картинки мало.** Провод, нарисованный
правильно, может оказаться разорванным: KiCad считает соединением только конец
провода или точку с junction, поэтому провод обязан быть разрезан там, где к
нему что-то подключается. На печати такая ошибка неотличима от исправной
схемы — в блоке 2 так молча распалась обратная связь канала 0.9 В.

## Как рисуются блоки

Каждый блок рисует свой скрипт `tools/blockNN_*.py`, общая машинерия — в
`tools/kicadsch.py`. Модуль печатает те же s-выражения, что писались бы руками;
библиотек KiCad в нём нет. Он же считает координаты выводов при повороте
символа — попасть в вывод надо точно, а руками это и есть главный источник
молчаливых обрывов. Скрипт блока идемпотентный:
перед вставкой выкидывает из схемы всё, что лежит внутри рамки своего блока, и
кладёт заново, — соседние блоки при этом не страдают, а UUID детерминированные,
поэтому повторный запуск не даёт diff'а на пустом месте.

У каждой детали заполнено поле `Источник` — раздел документа блока, откуда взят
номинал. Правило «ни одного номинала без ссылки на источник» проверяется прямо
по схеме, а не на доверии.

Грабли, на которые скрипты уже наступили и больше не наступают:

- `(hide yes)` внутри `(effects)` **не срабатывает, если рядом нет
  `(justify)`** — служебные ссылки `#PWR`/`#FLG` из-за этого печатались в PDF;
- **номер блока обязан входить в ссылку** служебного символа (`#PWR700`, а не
  `#PWR000`): иначе каждый блок начинает нумерацию с нуля и выдаёт ссылки,
  уже занятые соседом;
- `✓` и подобные знаки штриховой шрифт KiCad не рисует — в PDF выходит пустой
  квадрат. В подписях только то, что есть в шрифте.
