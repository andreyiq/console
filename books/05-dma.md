# Глава 5. DMA — данные летят без CPU

## Зачем нужен DMA

Без DMA каждый байт на экран — это работа CPU: прочитать из памяти, записать в
регистр SPI, подождать FIFO, повторить. Для кадра 480×320×3 байта = 460800 байт
это сотни тысяч итераций `write_volatile` + spin. CPU занят на 100%, а SPI всё
равно простаивает между записями (FIFO опустошается быстрее, чем CPU успевает
заполнить).

**DMA (Direct Memory Access)** — отдельный контроллер, который переносит данные
между памятью и периферией **сам**, без команд CPU. CPU только настраивает канал
(откуда, куда, сколько) и запускает; дальше железо копирует, а CPU свободен для
другого (или спит).

Для нашего flush'а дисплея: DMA качает байты из RAM-буфера прямо в TX FIFO SPI0.
CPU говорит «старт» и ждёт — SPI не голодает (FIFO всегда полон), CPU не крутит
байт-цикл. Выигрыш — и в скорости, и в свободном CPU.

## DMAC на F133

**DMAC** (раздел 3.9 мануала) — 16 каналов, сидит на шине MBUS. База `0x03002000`.
Тактуется от PSI_CLK через `DMA_BGR_REG` (CCU offset `0x070C`): бит 0 — gating
(0=маска, 1=пропуск), бит 16 — reset (0=assert, 1=de-assert).

### DRQ-порты

Каждый канал знает **порт источника** и **порт приёмника** — это номер устройства,
к которому привязан запрос данных (DRQ, Data Request). Таблица 3-11:

| port | источник | port | приёмник |
|------|----------|------|----------|
| 0    | SRAM     | 0    | SRAM     |
| 1    | **DRAM** | 1    | **DRAM** |
| 22   | SPI0-RX  | 22   | SPI0-RX  |
| 23   | SPI1-RX  | 23   | **SPI0-TX** |

Для нас: источник = DRAM (port 1, там лежит framebuffer), приёмник = SPI0-TX
(port 23, TX FIFO).

### Дескрипторная модель

F133 DMAC — **дескрипторный**: конфигурация одной посылки лежит в памяти как
**6 слов (24 байта, word-aligned)**. DMAC читает дескриптор, переносит данные,
по полю `link` переходит к следующему или останавливается (`0xFFFFF800` = конец).

```
word 0  Configuration   (формат как у DMAC_CFG_REGN)
word 1  Source Address  (младшие 32 бита 34-битного адреса)
word 2  Destination Address
word 3  Byte Counter     (сколько байт перенести)
word 4  Parameter        (старшие 2 бита адресов + доп.)
word 5  Link             (адрес след. дескриптора, 0xFFFFF800 = конец)
```

Это позволяет строить **цепочки** передач: несколько дескрипторов в памяти, DMAC
гонит их подряд без участия CPU. Для одного кадра хватит одного дескриптора.

### Биты Configuration (DMAC_CFG_REGN, 3.9.6.10)

| биты  | поле                | значения                          |
|-------|---------------------|-----------------------------------|
| 5:0   | SRC_DRQ_TYPE        | порт источника (1 = DRAM)         |
| 7:6   | SRC_BLOCK_SIZE       | 00=1, 01=4, 10=8, 11=16          |
| 8     | SRC_ADDR_MODE        | 0=Linear (адрес растёт), 1=IO     |
| 10:9  | SRC_DATA_WIDTH      | 00=8, 01=16, 10=32, 11=64 бит    |
| 21:16 | DEST_DRQ_TYPE       | порт приёмника (23 = SPI0-TX)    |
| 23:22 | DEST_BLOCK_SIZE     | 00=1, 01=4, 10=8, 11=16          |
| 24    | DEST_ADDR_MODE      | 0=Linear, 1=IO (FIFO фиксирован)  |
| 26:25 | DEST_DATA_WIDTH     | 00=8, 01=16, 10=32, 11=64 бит   |
| 31    | BMODE_SEL           | 0=Normal                          |

**Linear vs IO**: память — Linear (адрес инкрементируется, DMA читает
последовательно), FIFO периферии — IO (адрес фиксирован, DMA пишет всегда в один
регистр TXD, данные сами падают в FIFO).

Для DRAM → SPI0-TX, 8-бит:
```
config = (DEST_ADDR_MODE=IO << 24) | (DEST_DRQ=23 << 16) | (SRC_DRQ=1)
       = 0x01000000 | 0x00170000 | 0x00000001
       = 0x01170001
```

### Регистры канала (0x100 + N*0x40)

| смещение | регистр            | что делает                          |
|----------|--------------------|-------------------------------------|
| 0x100    | EN                 | бит 0 = запуск канала (auto-clear)   |
| 0x104    | PAU                | пауза/возобновление                  |
| 0x108    | DESC_ADDR          | адрес дескриптора в памяти           |
| 0x10C    | CFG                | конфиг (можно задать и регистром)    |
| 0x118    | BCNT_LEFT          | сколько байт осталось (для прогресса)|

## Запуск передачи (3.9.4.1)

1. Включить такт DMAC через CCU (`DMA_BGR_REG`).
2. Записать 6-словный дескриптор в память (word-aligned).
3. Записать адрес дескриптора в `DESC_ADDR_REG` канала.
4. Прочитать `DESC_ADDR_REG` обратно — убедиться, что запись прошла (мануал 3.9.4.3).
5. Записать 1 в `EN_REG` канала — DMAC читает дескриптор и стартует.
6. Ждать, пока `EN_REG` не сбросится (канал сам выключается по концу очереди).

## SPI-сторона: NDMA_MODE_CTL

Чтобы SPI-контроллер принимал данные от DMA, у него есть регистр
`SPI_NDMA_MODE_CTL` (offset `0x88`, 9.3.6.16). Биты 7:6 = `SPI_ACT_M`:

- `00` — dma_active всегда низко (DMA не пашет)
- `01` — dma_active всегда высоко
- `10` — **dma_active управляется DRQ** (то, что надо: SPI сам поднимает запрос,
  когда в TX FIFO есть место, DMA отвечает порцией данных)
- `11` — управляется контроллером (дефолт)

Ставим `10`, остальное по умолчанию → `0xA5` (дефолт `0xE5`, меняем биты 7:6
с `11` на `10`).

## Связка SPI + DMA для одного кадра

Поток байт: **DRAM → DMA → TX FIFO → MOSI → дисплей**.

1. `set_window` на весь экран + команда `0x2C` (Memory Write) + DC=data —
   всё как при CPU-flush. CS держим низко до конца.
2. Настроить SPI burst-счётчики: `MBC = MTC = BCC = 460800` (сколько байт
   отправить в этом обмене).
3. `NDMA_MODE_CTL = 0xA5` — SPI готов к работе с DMA.
4. Запустить DMA: дескриптор (src=framebuffer, dest=SPI TXD, count=460800),
   `DESC_ADDR_REG`, `EN_REG=1`. DMA начинает кормить FIFO.
5. `TCR = XCH | DHB | SS_OWNER` — старт обмена. SPI вычитывает FIFO и шлёт на MOSI;
   как FIFO пустеет — поднимает DRQ, DMA докладывает.
6. Ждём: сначала `DMA.EN` сбросится (все байты ушли в FIFO), потом `SPI.TCR & XCH`
   сбросится (SPI отправил последнее из FIFO). CS вверх.

Порядок «сначала DMA, потом XCH» удобен: DMA успевает наполнить FIFO до старта
обмена, SPI сразу начинает гнать без стартовой паузы.

## Замер времени

Чтобы увидеть выигрыш, меряем циклы CPU до и после flush (через `mcycle` CSR,
`riscv::register::mcycle::read()`). CPU-flush крутит байт-цикл и съедает много
циклов; DMA-flush — CPU просто ждёт (spin), но SPI работает на полной скорости
FIFO. Разница в циклах CPU = свободное время, которое можно потратить на
эмулятор NES, а не на перекладывание байт.

## Где это в коде

- `src/dma.rs` — драйвер DMAC: дескриптор, `Dma::Channel0.start/wait_done`.
- `src/spi.rs` — `prepare_dma` (burst + NDMA + XCH), `txd_addr`, `wait_burst_done`.
- `src/display.rs` — `flush_buffer_dma(buf)` связывает всё вместе.
- `src/main.rs` — `dma.init()` + `flush_buffer_dma` с замером `mcycle`.
- `src/ccu.rs` — `Peripheral::Dmac` (такт + reset).

## Что дальше

DMA готов кормить SPI без CPU. Следующий шаг — **двойная буферизация**: два
framebuffer'а, рисуем в один, DMA льёт другой, переключаемся. Так можно
рисовать кадр, пока предыдущий ещё льётся, — основа для анимации и эмулятора.
